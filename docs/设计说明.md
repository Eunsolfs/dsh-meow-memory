# 设计说明（0.32 fork）

为什么 meow-memory 这样设计。记录取舍与踩过的坑，不是功能清单。0.32 的改动原则：**保留上游正确的传输/调度设计，把夸大表述改成真实边界，把无界成本改成有界。**

---

## 1. 为什么静态手册放 system prompt，而动态内容进第一条用户消息

| 内容 | 去哪 | 为什么 |
|---|---|---|
| 静态记忆手册（数据总览 + 工具用法 + 写作准则） | **system prompt** 的固定 section | 文本恒定，因此**不会破坏 LLM provider 的 KV/上下文缓存** |
| 动态内容（soul/user 全量、设计原则、记忆导引） | **第一条用户消息的前缀** | 内容随工作区变化，放 system prompt 会让缓存每次失效 |

静态 section 名为 `meow-memory:guide`，order 130，紧随各 `tool:*` 说明之后，注册一次、文本恒定。记忆本身作为**独立 plugin snapshot 消息**放在真实 user 消息之前，**不改写用户 prompt**。

代价：静态部分（手册 + 全部工具描述/schema）在**每个请求**都占 ≈6.7k tokens（中文包实测）/ ≈6.3k（英文包）——这是本插件最大的固定成本，也是 0.32 在 README 里明确写出它的原因。

---

## 2. 为什么首轮不跑关键词命中

首轮只注入长期记忆快照，**命中从第二轮起**。原因：第一条用户消息与插件通知消息可能同批到达（如 approval policy 变更通知），若在首轮就做命中，命中内容会插到通知消息那一轮，而不是真实用户消息那一轮。

因此设计为：**快照紧贴插入到真实用户消息之前，命中绝不提前**。

---

## 3. 为什么命中基于条目关键词，而不是全文

全文匹配噪音大——一段记忆里出现某个词，往往不代表这条记忆与当前话题相关。所以命中基于条目关键词；**默认没有向量/语义检索**，0.35 起可用**可选**语义层（默认关、零网络）。

0.32 的真实打分（每消息命中，`src/bm25.ts` 的 `keywordHitScore`）：

```
关键词交集 × IDF × 查询覆盖率 × 指数近期权重 × importance 权重 × title 加成
```

- **查询覆盖率** = 命中的查询 token 数 / 查询 token 总数（0.32 修复：旧版分母是条目关键词 token 数，关键词写得越多覆盖率越低，**反向惩罚了 prompt 要求的 8–13 个关键词**）；
- **指数近期权重** = `0.05 + 0.95·exp(-ln2·ageDays/halfLifeDays)`，默认半衰 30 天；`importance ≥ 3` 只保留 0.85 下限。**0.35.1 起 age = `now − max(updated_at, last_accessed_at)`**：注入命中与 `memory_search` 命中会更新 `last_accessed_at`，最近被想起的记忆衰减更慢（rehearsal 式）；但**没有复习次数模型、没有调度**，`updated_at` 仍由 dream 封存/update 刷新——不是完整艾宾浩斯实现；
- **命中反馈** = `×(1 + 0.15·ln(1+hit_count))`，上限 2.0——旧版 `hit_count` 只写不读，0.32 起真正参与排序；
- **importance 权重** = `×(0.85 + 0.05·importance)`；
- **最低分门槛** `retrieval.minScore` 默认 0.35，低于它不注入。

`memory_search` 用的是 **BM25**（`ln(1+(N−df+.5)/(df+.5))`、k1=1.5、b=0.75、长度归一 + 近期权重），和上面的每消息命中不是同一套打分。旧文档把两者混称 BM25，0.32 改正。

**0.33 混合词法补分（fuzzy）**：BM25 是"整词/整 bigram 精确匹配"，同义变体、词形变化、CJK 词边界差异都会漏召回。额外加一层纯字符级相似度（零依赖、离线、确定性）：字符 bigram Jaccard + **0.25×trigram Jaccard**（NFKC、小写、只留字母数字；CJK 无需分词），噪声地板 0.2。它**只当 floor**：`score = max(BM25, 0.55·fuzzy·recency·importance)`；BM25 强命中时 max() 不改变排序，BM25 为 0/很弱时才补召回（每消息命中链路同理：`relevance = max(BM25 relevance, fuzzy)`，再乘遗忘权重）。**这不是 embedding/语义检索**：它只覆盖词法变体/词形/词边界，同义改写仍可能召回不到；无配置开关（纯 BM25 是测试/内部选项）。

**0.35 可选语义 floor（`retrieval.semantic`，默认关；0.35.1 审计修正）**：启用后 `semantic.ts` 调 OpenAI-compatible `/embeddings` 取向量，余弦相似度**同样只当 floor**：`relevance = max(词法, fuzzy, cos·weight·importanceWeight)`，含 **0.25 噪声地板**（cos < 0.25 按 0；负/零相似度按 0），`memory_search` 再 × recency、`explain` 带 `semantic`。**不做 rerank**，可能放进弱匹配。默认关 = **零网络**（未配置 endpoint 时 `semanticEnabled()` 为 false，所有调用点短路；网络只存在于 `semantic.ts`，静态审计可证）。**传输策略（0.35.1）**：只允许 `https://` 或 loopback `http://`（localhost/127.x/[::1]）；远程明文 http 直接拒绝并回退词法（零请求，避免正文/查询/Bearer 明文过网）。**延迟**：端点挂起时每条消息/检索/写入最多增加 `timeoutMs`（默认 5s）——不抛错、仍返回词法结果（连接被拒快速失败）；"never blocks"过强，已改为"bounded by timeoutMs"。数据/隐私：启用后**记忆正文/标题/关键词**与**用户消息/查询文本**发往你配置的端点；key 走环境变量（默认变量名未设置 → 无 key 请求；只有自定义变量名缺失才算未配置）。失败/超时/非 2xx/形状不对 → null，**绝不 throw**，静默回退词法。写入路径 `memory_remember`/`memory_update` 写后内联补 embedding；插件 apply 后**后台回填**全局库与各可信工作区（≤50 行/层；**0.35.1 冷启动先做只读信任判定再回填**，foreign 跳过；失败下次启动重试）；embedding 存在各表懒加的 nullable `embedding TEXT`（JSON）列，**1536 维 ≈31 KiB/行（1k 条 ≈30 MB）**，属明文派生数据。**不是本地模型**，换 embedding 模型会让已存向量失效（维度不同按 0 处理）。

## 4. 为什么"已见"要按会话记录

已见记忆（`injected` + `searched`）按会话记录在 `sessions/<id>.json`：

- **注入绝不重复**；
- `memory_search` 前 5 条按相关度无脑取（不排除已见/本会话建立的记忆），其余从排名后续绕开已见补齐；
- 收到会话压缩信号时**释放已见记录**，允许压缩后被再次命中。

前 5 条刻意不排除已见：如果一开始就排除，最相关的那几条永远取不到，检索会"越搜越偏"。

---

## 5. 为什么压缩后要重注入（以及为什么现在有上限）

会话被压缩后，下一个用户消息轮自动重新注入：长期记忆快照、本会话查阅过的项目全景、本会话写入/更新过的记忆原文。

压缩甩掉的"记性"一个回合补回来，AI 不会因为压缩突然失忆。

代价：旧版重注入**不设字符上限**（8 个项目 × 613 字符固定模板 + 20 条记忆原文），最坏 16k+ tokens。0.32 加 `budget.reinjectMaxChars` 默认 8000 字符，超出截断。

## 6. 为什么按窗口 dream，以及 0.32 给它加的笼子

原设计是夜间窗口；现在是**按窗口**：窗口空闲 ≥ `idleMinutes`（默认 3 小时）即进入允许触发状态，由该窗口自己的主 agent 整理，用的是该窗口的完整会话上下文。

分三轮：① 原子记忆 project/fact/lesson/rules/soul/user；② topic；③ 项目总结（涉及具体项目时）。

成本：每轮都是**全上下文请求**。30k token 的会话一次 dream ≈ 90k input tokens；100k 会话 ≈ 300k，且旧版不检查上下文预算。整理指令、模型回复、工具调用还会**永久留在主会话历史**（UI 折叠只是视觉收纳），一次 dream 约 +8–15k durable tokens。

0.32 的门（全部满足才自动跑）：

| 门 | 默认 | 修复 |
|---|---|---|
| 窗口有 **live agent**，绝不 `agents.resume()` | `dream.requireLiveAgent: true` | #49（复活裸 agent 丢 26 个内置工具） |
| 估算上下文 ≤ `budget.dreamMaxContextTokens` | 40000 | 防止大窗口 dream 爆上下文/账单；**后续轮次重新估算**，超限提前收尾（未封存，之后可再 dream） |
| 每窗口每天 ≤ `budget.dreamMaxPerWindowPerDay` | 1 | 无界频次 |
| 进程级全局每天 ≤ `budget.dreamMaxPerDayTotal` | 12 | N 个窗口不再 = N 倍自动花费（计数进程级滚动 24h，重启清零） |
| 排除 `status='archived'`、每轮清单 ≤ 60 条（按 `updated_at` 最新取） | 固定 | 旧版把归档条目反复喂给 dream，prompt 单调增长；近期更新过的老条目不再被饿死 |
| 跳过原因写日志 | — | 可解释 |

手动 `/dream` / `memory_dream` 不过这些自动闸（手动 = 明确意愿；代码里只有自动路径调用 `evaluateAutoDreamGate`）：峰时/频次/上下文闸都不限制，按**完整会话上下文**连跑最多 3 轮（atomic / topic / 项目总结）。上下文很大时请先 `/compact` 再 dream。

**0.34 隔离路径（`dream.isolated: true`，默认关）**：自动 dream 改为在**空上下文 spawn 子会话**执行（`inheritsParentContext === false` 的 provider），主会话没有 model-visible 的 dream 轮 → **主会话上下文 0 增长**。子会话 prompt = dream 三个文案槽 + 最近 user/assistant 文本与工具名 digest（不含工具结果/插件通知）+ 条目清单，单条 prompt 由 `isolatedMaxPromptChars`（默认 20000 字符）封顶；因此**整理质量低于主上下文路径**。主上下文大小闸对隔离路径不生效（子 prompt 独立封顶），频次/冷却/峰时/进程级上限仍生效；成功收尾先 `adoptSessionEntries` 把子会话写入条目归到父窗口再封存（部分结果保留），失败/超时/中止回退主 agent，HMR/dispose 会取消在途任务；`delegate.model` 也用于子会话。**隔离 dream 无法从 UI 中止**。

## 7. 为什么有峰时抑制（以及默认值可能不适合你）

`suppressWindows` 默认 09:00–12:00、14:00–18:00（`timeZone` 默认 `Asia/Shanghai`），及各自开始前 15 分钟不触发。

这组默认值来自上游，是**按智谱/GLM 的峰谷电价时段**设的；DeepSeek 的优惠时段不同。用哪家模型请按自己的价格窗口改。峰时结束后下一个检查周期自动触发；进行中的 dream 不打断。

---

## 8. 为什么 `rules` 要防 churn

长期稳定的 `rules` 反复重审会变成"没话找话"式更新。`dream.rulesReviewDays` 默认 2 天：`updated_at` 距今超该天数的稳定准则不进 dream 第 1 轮清单；`0` = 不过滤。

---

## 9. 为什么"恢复默认"要区分出厂默认与 patch 基线

设置页原来的「恢复默认」只做"删掉 user 层字段、显示回落 base"，而 base = 出厂默认 + patch 基线，于是 patch 里手编的非默认值会被当成"默认"还给用户。

现在语义统一为：**恢复默认 = 回到插件出厂默认**。默认值单一来源（`src/defaults.ts`），host 与 client 共用。0.32 新增的 `security`/`budget`/`retrieval` 字段**没有进设置页**，因此"恢复默认"不受影响，也不会在设置页显示。

---

## 10. 为什么不用独立 fork 子代理执行整理

独立 fork 子代理执行方式已于 **v0.24 移除**。现在反思轮和 dream 各组**始终在主窗口执行（steer）**——prompt、模型回应、工具调用落在主会话 log（折叠 UI 负责视觉收纳）。

换模型用 `delegate.model`：反思/梦境轮发起的每个 LLM 请求经 `agent/request` waterfall 覆盖 provider/model，轮次结束自动换回。实现是无状态的。

> #71（未修，上游 issue）：配置了 `delegate.model` 时，反思轮结束后宿主侧 `request/header` 投影可能被污染，后续普通请求继续跑在 delegate 模型上，直到手动切回。默认 `delegate.model` 为空 → 不触发。

---

## 11. 为什么 dream 要防重复

四道机制：check 门（DB 原子 60s 检查节流）、start 幂等抢占（`dream_pending`）、中断自愈、孤儿收尾（跨实例/热重载）。另外：插件注入轮的事件不刷新窗口活跃度——已 dream 的窗口不会反复被 dream。

> #66（未完全修复，上游 issue）：一次 dream 后会话工具集可能被锁在 9 个精简工具，需重启 dsh 才能恢复。插件侧没有设置工具过滤，疑似宿主后台轮次策略未还原。0.32 的自动 dream 加了 live-agent 门（不再走 `resume` 的裸 agent 路径），但**手动 dream 仍可能触发**，见 [CHANGELOG](../CHANGELOG.md) 的已知限制。

---

## 12. 为什么会话列表图标只追加/只移除自有节点

图标放进 dsh 会话行状态槽位：**只追加/只移除自有节点，不改写 React 拥有的子节点**。整槽替换会令 React 虚拟 DOM 失同步，commit 抛 `removeChild NotFoundError` 把侧边栏整树卸载。

行定位读 React fiber（`__reactFiber$` 内部属性）拿会话行渲染 key = session id，不依赖标题匹配。数据走全页共享的 60s 轮询 diff。

**这是"尽力而为"的宿主内部结构依赖**：0.2.x 补丁更新可能让它静默失效。只影响外观，不影响记忆数据。

---

## 13. 为什么全局标记要随语言走

全局标记取自当前语言包 `labels.md` 的 `project.global`（中文包「全局」；英文/葡语包 `global`）。必须随语言走——否则英文包里模型写的 `"global"` 会被当成一个叫 global 的项目：全局 rules 不再注入、项目列表里凭空多一个项目。取不到时回退真值（检索热路径不能因为文案文件过期就 throw）。

---

## 14. 为什么零运行时依赖

`node:sqlite`（Node ≥22.13 默认可用；22.5–22.12 需 `--experimental-sqlite`）+ 自包含 esbuild 产物（`lib/index.js`）。无原生模块。

## 15. 0.32 的信任模型（安全设计）

旧版有两个 P1（#64-1 / #64-2），0.32 用三道闸修复：

1. **工作区库信任标记**：只有 `memory.db` **文件根本不存在**时才自动创建并信任；**任何已存在的库（哪怕空表/schema-only）都默认 untrusted**（防"预置空库 + SQLite trigger"投毒）。创建库时写 `.owner.json`（`{schema:1, installId, workspace, createdAt}`），信任判定要求：`installId` 等于本机**随机**安装 id（`$DSH_HOME/storages/meow-memory/install-id`，不是机器指纹）、且 `workspace` 与当前路径一致；伪造/他机/挪位标记一律不可信，install-id 落盘失败时 **fail-closed**。untrusted 库**不会被正常聊天轮打开**（不升级/不建索引/不迁移/不读，只有只读探针），内容不注入，**记忆工具读写、dream 与反思全部拒绝**，会话里提示一次。显式 `security.trustWorkspaceMemory: true` 才放行。`autoMigrate` 同时默认关，避免工作区自带 `PROJECT.md` 被零交互导入。
2. **memory_home 默认只读**：该工具是模型可直接调用的，搬动全局目录会改变日志 / window-index / migrate 状态等实例数据的落点——模型不该有这种文件系统副作用。现在默认拒绝切换，`security.allowHomeSwitch: true` 才开放。
3. **prompt 覆盖层目录固定**：覆盖层从 `$DSH_HOME/storages/meow-memory/prompts/` 固定解析（`$DSH_HOME` 缺省 `~/.dsh`），**不跟随** `homeDir` / `memory_home` / `MEOW_MEMORY_HOME`，旧位置不再读取（无 fallback），切断"切目录 = 换注入文案"。

另外：路径比较经 **realpath 归一**（junction / 映射盘 / subst 别名不再误判 foreign，解析不了时仍 fail-closed）；信任闸覆盖 **HTTP 数据路由、会话窗口活动跟踪、启动期 window-index 恢复**（0.32.1：这些路径都不为记账去打开/升级 untrusted 库；POST `skip-dreams` 对 untrusted 返回 403）。写库时自动补 `<记忆目录>/.gitignore`（没有就写 `*`；已存在但缺 `*` 行也追加一行，防 `!*` 重新包含），防止 `git add .` 把明文记忆提交进仓库；`security.debugLogs` 默认关的是 `perf.log` 与 settings/configEditor 诊断 dump，`dream-debug.log` 仍默认写最小信息（会话 id/计数/跳过原因，无记忆正文；48h 清理 + 5MB 轮转），error 日志只在出错时写；卸载**不删数据**（路径见 README），这是有意的——插件不应替用户决定删记忆。

**没做的**：记忆库不加密（明文 SQLite），没有 per-entry 权限，没有网络外联（插件自身零请求）。明文库所在的磁盘/备份/同步盘仍是信任边界。

## 16. 0.33：用户级全局记忆与分层存储

0.32 的"全局"只在单个工作区内全局；0.33 把它改成**用户级**两层：

```
<activeHomeDir>/global/memory.db        ← 用户级：soul / user / rules(全局)，跨工作区
<workspace>/<projectDir>/memory.db      ← 工作区级：project / fact / lesson / topic / rules(项目)
```

- **为什么不直接全部搬进全局库**：project/fact/lesson/topic 是工作区语义（同一个 cwd 的项目上下文），放全局会互相污染；soul/user/全局 rules 才是"用户是谁"级别、天然跨工作区。分层是"把正确的层放到正确的生命周期"。
- **迁移**：每个工作区首个可信会话把原有 soul/user/全局 rules **按原 id** 复制进全局库（保 id/时间戳，注入去重与链接不破），然后**归档工作区原件**（可恢复；否则快照与 dream 会双计）。幂等标记写在工作区库 `dream_meta`（`globalmigrated:v1:<dir>`）；只对可信工作区执行，foreign 库不碰（迁移不跨信任边界读）。
- **回退**：全局库缺失/未受信/不可用时自动退回 0.32 单工作区行为。这样"全局库被删/从别的机器同步过来"都不会让插件不可用，也不会把陌生数据当用户记忆。
- **全局库信任闸**：`<activeHomeDir>/global/.owner.json`（installId 标记、`workspace: ''` 无工作区绑定）；不存在→创建，已存在无有效标记→foreign；**没有** `trustWorkspaceMemory` 配置信任档（全局库是"用户自己"的数据，不接受"信任陌生库"这种开关）。
- **工具路由**：写路径按层级分流（soul/user/全局 rules → 全局库），读路径两库并查、按 id 去重（同 id **active 优先于 archived**，避免迁移归档副本遮住正本）；`memory_project` 只读工作区库（项目全景是工作区语义）。
- **Windows EPERM**：`homeDir` / `memory_home` 切目录会搬全局库，搬前先 `closeGlobalDb()`（Windows 上打开的 SQLite 文件阻塞 rename）。

**已知边界**：dream/反思仍只整理工作区库（全局条目靠工具/反思维护）；迁移会把工作区原件归档，全局库丢失不会自动回灌；`backup.enabled` 自 0.34 起同时备份工作区库与全局库（全局库为空/未受信时跳过）。

## 17. 0.34：隔离 dream（主会话 0 增长）

0.33 的自动 dream 仍是主会话里的全上下文请求：一次 dream 会在主历史里留下整理指令/回复/工具调用（≈+8–15k durable tokens），大窗口还会被 `dreamMaxContextTokens` 闸挡住。0.34 把**自动** dream 移到**隔离 spawn 子会话**（默认关）：

- **为什么是 spawn 而不是 fork**：`fork` 会继承父会话完整 transcript（等于把主上下文又搬一遍）；`spawn` 是空上下文新会话，只拿到我们给的 prompt/digest/清单，主会话因此 **0 增长**。
- **进程内/跨进程语义**：租约仍用工作区库（`claimDream`/心跳），`dreamiso:<sid>` meta 记录在途任务（诊断用）；子会话在同一个 workspace/cwd 调 `memory_*`（**继承父会话的 agent preset**，工具可见性取决于该 preset），成功后 `adoptSessionEntries(childId, parentSid)` 把 `source_session` 归到父窗口，再走既有 `stampDream`/`finishDream` 收尾；失败/超时/中止按既有失败计数重试（3 次封存）并回退主 agent 路径。
- **启动兼容（0.34.1 修复）**：0.34.0 的 `startActivation` 曾带 `request.maxDepth: 0`；DSH 0.2.1 把 `maxDepth` 读成**子会话自身允许的深度**，直接以 `SubagentDepthError: subagent depth 1 exceeds maxDepth 0` 拒绝启动 → `dream.isolated: true` 时自动整理实际完全不跑。0.34.1 **不传 `maxDepth`**（宿主默认 1）。启动被拒（同步或异步：深度/容量/鉴权）不再静默释放：同步失败返回 `'unavailable'`、同一轮扫描回退主 agent dream；异步拒绝释放租约并在同一轮启动主 agent dream（日志 `isolated-dream rejection -> main-dream fallback`）。
- **生命周期**：超时 `isolatedTimeoutMinutes`（默认 20 分钟）→ dispose 子会话、释放租约；HMR/dispose 调 `disposeIsolatedDreams()` 取消在途任务并释放租约（防僵尸租约）；`isolatedArchiveChild` 在子会话 settle 后的 `finally` 里归档（**成功/失败都会归档**，留下一份明文子会话副本）。
- **成本与质量取舍**：子会话 token 仍计费；digest 只含最近 user/assistant 文本 + 工具名（不含工具结果），prompt 有 `isolatedMaxPromptChars` 上限，所以**整理质量低于主上下文路径**；且**无法从 UI 中止**。主上下文大小闸对隔离路径不生效，频次/冷却/峰时/全局每日上限仍生效。
- **回退**：`subagents` 服务 / `spawn` provider 缺失或 `inheritsParentContext !== false` → 记一次日志后走 0.32 主 agent dream；启动被拒同样回退；主 agent 路径仍保留（手动 `/dream` 永远走它）。

## 18. 0.35：可选语义检索（默认离线）

0.34 的检索只有 BM25 + 字符 n-gram fuzzy，同义改写仍召回不到。0.35 加**可选** embedding 语义层，但把默认值定成"关"：

- **为什么默认关**：embedding 必须依赖外部服务（插件不打包本地模型），开启意味着把**记忆正文与用户查询文本**发到该服务；默认关 = 零网络、零隐私外发，行为与 0.34 完全一致。
- **为什么是 floor 而不是 rerank**：与 fuzzy 同一思路——只在 BM25/词法弱时补召回，避免语义分压过精确关键词命中；代价是可能放进弱匹配。**0.25 噪声地板**挡住无关条目靠偶发小相似度混入，负/零相似度按 0。
- **数据流**：`semantic.ts` 独占网络（`POST {baseUrl}/embeddings`，LRU 256）；写入路径内联补 embedding（受 `timeoutMs` 约束）；插件 apply 后后台回填历史条目（全局库 + 各可信工作区，≤50 行/层，失败静默、下次启动重试）。`embedding` 以 nullable JSON `TEXT` 列懒加到 7 张表，随库/备份走。
- **失败语义**：超时/网络错误/非 2xx/坏形状/无 `fetch` 一律 null，调用方静默回退纯词法；语义层故障只会带来有界延迟（≤`timeoutMs`），不会让注入/检索/写入失败。
- **已知边界**：不是本地模型；向量是模型特定的（换模型/维度不同 → 按 0 处理，需重写或重新回填）；设置页不暴露该配置；`weight: 0` 只是不算语义分，想完全离线必须 `enabled: false`。

## 19. 0.36：全局记忆可视化编辑 + 下轮重注入

用户级全局记忆（soul/user/全局 rules）此前只能通过模型工具或直接改 SQLite 维护。0.36 在设置页加一个**用户显式操作**的可视化编辑器，并让它改完能真正影响后续会话，同时不引入新的自动花费。

- **为什么走设置页而不是新工具**：编辑用户级长期记忆是"用户自己的决定"，不该消耗模型轮次或把模型卷进 UI 交互；设置页是用户显式通道，语义上接近手动 `/dream`（权威性高，但 dream 之后仍可能重整条目）。**没有新增工具、没有新增配置项**。
- **数据路径**：设置页 UI → 插件私有 `GET/POST /meow-memory/global-memory`（与其他插件路由同款 auth gate）→ `global-edit.ts` 纯数据层 → 全局库。列表只含 soul/user/全局 rules（含 archived/stale）；写入校验 content 1–4000、keywords ≤30（空则从内容分词派生）、importance 1–100；无硬删除（归档）；同 id 并发 **last-write-wins**。
- **为什么保存后要"打标记"而不是直接改历史**：已发生的注入消息属于历史，改写它会破坏会话一致性且可能重复计 token。0.36 复用既有"压缩后重注入"通道：保存成功后给相关会话（window index + `sessionPersistence` 带 cwd、且已有**受信** memory.db）打 `reinject` 标记；这些会话在**下一轮用户消息**重新注入更新后的全局记忆，并清掉标记。**零即时 token**、不额外发模型请求；没有下一轮消息的会话保留旧快照。归档/恢复同样触发（注入内容变了）。
- **为什么只碰全局库**：工作区库属于各 cwd 的项目上下文，不应被一个跨工作区的编辑器批量改写；全局库未受信/foreign 时编辑器显示警告并拒绝写入（不打开 foreign 库），与信任模型一致。
- **语义联动**：content/keywords 变化会清掉该条 embedding（避免用旧向量召回）；下次 apply 的后台回填或下一次写入重建；仅 importance 变化保留向量。编辑器自身不发任何 embedding 请求。
- **残余边界**：仅全局作用域；要等会话下一轮消息才生效；无硬删除/批量导入/冲突合并；路由是插件私有（非公开 API）；last-write-wins；归档条目不注入但仍保留在库中。

## 20. 已知设计债（0.36 更新）

| 问题 | 影响 | 为什么没修 |
|---|---|---|
| **项目级记忆仍按工作区隔离** | `project` / `fact` / `lesson` / `topic` 跟 cwd 走；换工作区后项目记忆是新的（soul/user/全局 rules 已跨工作区，0.33） | 项目记忆共享需要库级归属模型，留待后续 |
| **默认无语义召回** | `retrieval.semantic` 默认关；不开只有 BM25 + fuzzy，同义改写仍可能召回不到 | 语义层依赖外部 embedding 服务，默认关是隐私/可用性选择（opt-in） |
| **语义层只是 floor、不是 rerank** | 0.25 噪声地板之上可能放进弱匹配；不保证语义排序质量 | 与 fuzzy 同一取舍：避免压过精确关键词命中；重排需要可信的 cross-encoder 模型 |
| **语义向量绑定模型** | 换 endpoint 模型/维度后，旧向量按 0 处理；已写向量不会自动重算 | 向量是模型特定的；需重写条目或清空后重新回填 |
| **设置页不暴露语义配置** | `retrieval.semantic` 只能改 profile patch | 设置页代码不在本轮范围；装后按自测清单手改配置 |
| **embedding 发送记忆正文** | 启用后记忆正文/标题/关键词与用户查询文本会发往配置的端点 | 这是语义检索的必要条件；默认关 + 文档明示，由用户选择服务方 |
| **编辑器 last-write-wins** | 同一 id 在多个设置页/工具里并发编辑时后写覆盖先写，无冲突检测 | 个人插件单用户场景，引入版本号/乐观锁成本高于收益 |
| **编辑器无硬删除** | 只能归档/恢复，归档条目不注入但仍占库 | 与"插件不替用户删记忆"的既有原则一致；需要彻底删除用 `memory_forget mode=delete`（工具通道） |
| **编辑器只覆盖全局作用域** | 项目级 rules/fact/lesson/topic 不在 UI 里，仍需 `memory_*` 工具 | 工作区级数据跨 cwd 语义复杂，UI 批改风险高；保持工具通道 |
| **保存要等下一轮消息才生效** | 没有后续用户消息的会话保留旧快照 | 不改写历史/不即时发模型请求是刻意取舍；下一轮复用压缩重注入通道 |
| **语义请求有延迟上界** | 端点挂起时每条用户消息/检索/写入最多增加 `timeoutMs`（默认 5s）延迟（不抛错、仍返回词法结果） | 同步等待是为了让语义分参与本次检索；调小 `timeoutMs` 或关 `enabled` 可消除 |
| **向量占库体积** | embedding 以 JSON 文本存 DB/备份，1536 维 ≈31 KiB/行（1k 条 ≈30 MB），且是明文派生数据 | 向量检索需落盘；想省空间可减少启用条目或关闭语义（关后不写新向量） |
| **远程明文 http 端点被拒** | 只允许 https 或 loopback http；远程明文 http 配了也不发请求（回退词法） | 语义请求会带记忆正文/查询/Bearer；拒绝明文是安全默认 |
| **dream 不整理全局库** | 全局条目靠工具/反思维护，不进 dream 三轮 | dream 是工作区窗口语义，全局整理需独立调度 |
| **迁移归档工作区原件** | 全局库丢失后原行不会自动回灌（内容仍在 archived） | 自动回灌会与"全局库被删=用户意图"冲突；提供 `memory_forget mode=restore` 手动恢复 |
| **隔离 dream 不可从 UI 中止** | 只能等超时/完成/失败；dispose/HMR 会取消 | 宿主子代理 activation 无 UI 中止入口（0.34 记录为限制） |
| **隔离 dream 质量低于主路径** | digest 不含工具结果/插件通知，prompt 有上限；部分任务理解不足 | 与"主上下文 0 增长"直接冲突；默认关，按需开启 |
| **子会话工具可见性取决于父 preset** | 子会话继承父会话 agent preset；若该 preset 未暴露 `memory_*`，子会话无法写记忆（隔离整理无效） | 宿主子代理继承语义；0.34.1 记录为残余风险，不可用回退主窗口 dream |
| **归档子会话留明文副本** | `isolatedArchiveChild` 在 settle 后（成功/失败）归档子会话，磁盘上留一份明文 transcript | 归档是宿主 `workspaceRegistry.archiveSession` 语义；可设 `false` 不归档 |
| **全局库备份依赖 dream 触发** | `backup.enabled` 的全局库备份发生在 dream 收尾（主/隔离路径都会触发）；不做定时备份 | 备份链路沿用 dream 收尾钩子 |
| **无索引的检索** | 每消息 4 次全表扫描；几百条无感，几千条是性能悬崖 | T1 加了索引，但大规模仍需实测 |
| **#66 宿主侧工具锁** | 手动 dream 后工具集可能缩水，需重启 | 上游 / 宿主问题，插件侧无法根治；只能规避自动路径 |
| **#71 delegate 模型污染** | 配了 `delegate.model` 才可能触发 | 宿主侧投影问题；默认空值不触发 |
| **设置页 0.2.x 保存链路** | 可能渲染但不落到 apply | 设置服务改版，非本次加固范围；装后按自测清单验 |
| **pt-br 检索弱** | 无葡语词干/停用词归一化 | 需要葡语 NLP，超出范围 |
| **dream 历史持久占 token** | 折叠只是视觉收纳 | 宿主没有"隐藏消息"语义；彻底解决需宿主支持 |
| **明文 PII** | 记忆正文可能含隐私/密钥 | 加密会引入密钥管理，个人插件不划算；靠 `.gitignore` + 环境边界 |
